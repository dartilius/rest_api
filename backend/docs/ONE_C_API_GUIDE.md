# API вещания для интеграции с 1С

Этот документ описывает рабочий сценарий от данных 1С до фактического эфира:
как выбрать точку, загрузить контент, собрать плейлист, создать заказ и понять,
что именно сделал Player.

Примеры используют адрес `https://api.example.ru`. Замените его адресом среды.
UUID и токены в примерах вымышлены.

Интерактивные версии схемы доступны в приложении:

- `GET /api/docs/` — Swagger UI;
- `GET /api/redoc/` — ReDoc;
- `GET /api/schema/` — схема OpenAPI (`?format=json` для JSON).
- `GET /docs/` — ReDoc из той же актуальной схемы;
- `GET /api/integration-guide.md` — это руководство для передачи разработчику 1С.

## 1. Как устроен обмен

```text
1С / оператор
    │  JWT: access_token <JWT>
    ▼
Backend API
    │  создаёт команду и следит за её редакцией
    ▼
Content Player
    │  Station <station_token>
    ├─ подтверждает доставку и применение
    └─ отправляет события фактического воспроизведения
```

У системы два разных контура.

| Контур | Кто обращается | Заголовок **`Authorization`** | Для чего |
|---|---|---|---|
| Управление | 1С, веб-интерфейс, сотрудники | `access_token <JWT>` | Точки, файлы, плейлисты, заказы, просмотр состояния |
| Станция | Установленный Content Player | `Station <station_token>` | Получение команд, квитанции доставки, состояние и факты эфира |

1С использует только контур управления. **`station_token`** нельзя хранить в 1С
и нельзя передавать в запросы файлов, плейлистов или заказов.

### Что означает «успешно» на разных этапах

| Этап | Где смотреть | Что подтверждено |
|---|---|---|
| API принял запрос | HTTP `200` или `201` | Данные прошли проверку и записаны на сервере |
| Команда доставлена | **`delivery.status`** | Player получил или применил нужную редакцию |
| Контент вышел в эфир | **`actual_playback`** и события | Player сообщил о запуске/завершении воспроизведения |

HTTP `201` при создании заказа не означает, что ролик уже скачан или проигран.

## 2. Авторизация 1С

### Получение токенов

```http
POST /auth/jwt/create/ HTTP/1.1
Host: api.example.ru
Content-Type: application/json

{
  "email": "integration@example.ru",
  "password": "<пароль из защищённого хранилища>"
}
```

Ответ:

```json
{
  "refresh": "<refresh JWT>",
  "access": "<access JWT>"
}
```

Во всех рабочих запросах передавайте **`access`** так:

```http
Authorization: access_token <access JWT>
```

В этом проекте используется префикс **`access_token`**, а не `Bearer`.

### Обновление access token

```http
POST /auth/jwt/refresh/ HTTP/1.1
Host: api.example.ru
Content-Type: application/json

{
  "refresh": "<refresh JWT>"
}
```

Сервер включает ротацию refresh token. Если в ответе пришёл новый
**`refresh`**, 1С должна атомарно сохранить его вместе с новым **`access`**.
Пароль и токены нельзя писать в журнал запросов 1С.

## 3. Идентификаторы: что хранить в 1С

| Поле | Сущность | Для чего хранить |
|---|---|---|
| **`code1c`** | Точка вещания | Стабильный бизнес-ключ для поиска точки по данным 1С |
| **`nomenclature.id`** | Точка вещания | UUID, который передаётся в заказе как **`nomenclature`** |
| **`file.id`** | Медиафайл | UUID файла для состава плейлиста |
| **`playlist.id`** | Плейлист | UUID набора контента для заказа |
| **`order.id`** | Заказ эфира | UUID для чтения состояния, изменения и отмены |
| **`order.revision`** | Редакция заказа | Версия, которую должен применить Player |
| **`installation_id`** | Установка Player | Технический идентификатор установки; обычно 1С не нужен |

Не используйте **`id_tachka`** или название точки как внешний ключ заказа.
Название может измениться, а технические поля старых Player не являются
контрактом 1С.

## 4. Найти точку вещания

Точка вещания в API называется **номенклатурой**. Карточку можно получить по
UUID или по **`code1c`**. Для первичной привязки 1С используйте точный код:

```http
GET /api/nomenclatures/0000012345/ HTTP/1.1
Host: api.example.ru
Authorization: access_token <JWT>
```

Фрагмент ответа:

```json
{
  "id": "00000000-0000-0000-0000-000000000101",
  "name": "Магазин на Мира, 10",
  "code1c": "0000012345"
}
```

Сохраните **`id`** как UUID точки. Ответ `404` означает, что сопоставление
справочника отсутствует; заказ создавать нельзя, пока оператор не исправит
привязку.

Для спискового и ручного поиска доступен
`GET /api/nomenclatures/?code1c=...`, а также фильтры **`search`**, **`name`**,
**`id`**, **`brand_id`**, **`status`** и другие. Ответ списка сокращён и имеет
поля **`count`**, **`next`**, **`previous`**, **`results`**. Автоматический обмен
1С должен использовать прямой запрос карточки по точному **`code1c`**.

## 5. Загрузка файлов

### Типы файлов

| **`type`** | API-тип | Назначение |
|---:|---|---|
| `0` | `music` | Музыка или обычное аудио |
| `1` | `video` | Видео |
| `2` | `image` | Изображение |
| `3` | `ticker` | Бегущая строка |
| `4` | `ad` | Рекламный файл |

Подтип файла в админке служит для классификации и не определяет правила
заказа. То, является ли заказ рекламным, задаёт **`placement`**.

### Новый JSON-запрос

`POST /api/files/` принимает JSON. Поле **`source`** имеет исторический формат:

```text
name:<имя>.<расширение>;base64,<данные base64>
```

Пример:

```http
POST /api/files/ HTTP/1.1
Host: api.example.ru
Authorization: access_token <JWT>
Content-Type: application/json

{
  "type": 4,
  "source": "name:promo-october.mp3;base64,SUQzBAAAAAAA...",
  "tags": [
    {"name": "1С"},
    {"name": "Кампания РК-1042", "color": "#3874CB"}
  ]
}
```

Успешный ответ `201` содержит созданный **`id`**, вычисленные **`hash`**,
**`size`**, **`length`**, имя и временную ссылку **`url`**. URL не храните как
постоянный: срок подписанной ссылки ограничен, для скачивания запрашивайте файл
снова.

`POST /api/source/` принимает multipart-файл, но помечен как устаревший и
сохранён для старой админки. Новая интеграция 1С использует `/api/files/`.

### Поиск уже загруженного файла

Перед повторной загрузкой можно искать по контрольной сумме или имени:

```http
GET /api/files/?hash=<md5+sha256>
GET /api/files/?name=promo-october
GET /api/files/?search=РК-1042
```

**`hash`** — серверная комбинация MD5 и SHA-256. При таймауте после `POST`
сначала выполните поиск: слепой повтор может вернуть ошибку дубликата.

## 6. Плейлисты

Плейлист отвечает на вопрос **«какие файлы и в каком порядке воспроизводить»**.
Заказ отдельно отвечает на вопросы **«на какой точке, в какой период и по
какому правилу»**.

### Два формата состава

| Формат | Поле | Когда использовать |
|---|---|---|
| Структурированный | **`items`** | Все новые интеграции; порядок; аудио с закреплёнными картинками; смешанный визуальный фон |
| Устаревший плоский | **`files`** | Совместимость со старыми клиентами; только простой список файлов одного типа |

В одном запросе нельзя передавать одновременно **`items`** и **`files`**.

### Создать аудиорекламу с картинками

```http
POST /api/playlists/ HTTP/1.1
Host: api.example.ru
Authorization: access_token <JWT>
Content-Type: application/json

{
  "name": "РК-1042 — аудио и баннеры",
  "description": "Синхронизировано из документа 1С РК-1042",
  "items": [
    {
      "file": "00000000-0000-0000-0000-000000000011",
      "images": [
        "00000000-0000-0000-0000-000000000021",
        "00000000-0000-0000-0000-000000000022"
      ]
    },
    {
      "file": "00000000-0000-0000-0000-000000000012",
      "images": []
    }
  ]
}
```

Здесь **`file`** — основной аудиоролик, а **`images`** — картинки только для
него. Когда Player воспроизводит следующий аудиоролик, он использует картинки
следующего элемента.

### Поля элемента **`items[]`**

| Поле | Запись | Чтение | Назначение |
|---|---:|---:|---|
| **`file`** | да | да | UUID основного файла |
| **`images`** | нет, по умолчанию `[]` | да | Упорядоченные UUID картинок для этого аудио |
| **`position`** | нет | да | Позиция основного элемента, начиная с нуля |
| **`file_name`** | нет | да | Имя основного файла |
| **`file_url`** | нет | да | Временная ссылка на основной файл |
| **`image_files`** | нет | да | Подробности картинок: **`id`**, **`name`**, **`url`**, **`position`** |

Правила:

- от 1 до 1000 основных элементов;
- один основной UUID нельзя повторять;
- картинки можно прикреплять только к аудиофайлу;
- в **`images`** разрешены только активные файлы типа `2` (`image`);
- до 1000 картинок на один элемент;
- до 10 000 ссылок на основные файлы и картинки в одном плейлисте;
- порядок элементов и порядок картинок сохраняются.

Аудио определяется как файл типа `0` либо файл типа `4` с аудиорасширением
`.mp3`, `.wav`, `.ogg`, `.flac`, `.aac`, `.m4a`, `.wma` или `.opus`.

### Получить полный состав

```http
GET /api/playlists/00000000-0000-0000-0000-000000000201/ HTTP/1.1
Authorization: access_token <JWT>
```

В ответе есть оба представления:

- **`files`** — плоский список основных файлов для совместимости;
- **`items`** — точный порядок и связи «аудио → картинки».

Для структурированного плейлиста источником истины является **`items`**.
У простого плейлиста **`items=[]`**: состав читается из **`files`**.

### Изменить метаданные или полностью заменить состав

```http
PATCH /api/playlists/00000000-0000-0000-0000-000000000201/ HTTP/1.1
Host: api.example.ru
Authorization: access_token <JWT>
Content-Type: application/json

{
  "description": "Редакция 2 из 1С",
  "items": [
    {
      "file": "00000000-0000-0000-0000-000000000011",
      "images": ["00000000-0000-0000-0000-000000000023"]
    },
    {
      "file": "00000000-0000-0000-0000-000000000014",
      "images": []
    }
  ]
}
```

Переданное **`items`** — полный новый снимок. Сервер заменяет им весь прежний
порядок и все привязки картинок. Если ни **`items`**, ни **`files`** не переданы,
состав не изменяется. Поэтому 1С должна сначала собрать полный желаемый список, а затем
отправить его одним запросом.

**`PATCH files`** заменяет основные файлы; картинки у оставшихся аудио
сохраняются. Новый файл добавляется без сопровождения. Не передавайте **`files`**
и **`items`** одновременно.

Изменение состава активного единого заказа повышает **`revision`** и создаёт
новую команду доставки. Повтор того же состава команду не создаёт. Ошибка
подготовки команды откатывает плейлист и редакции заказов вместе.
Пустой состав разрешён при PATCH только без активных заказов.
Если плейлист используется в активных старых **BgOrder/AdOrder**, полная замена
**`items`**/**`files`** запрещена: используйте прежние add/remove либо сначала
отмените эти заказы. Изменять название и описание можно.
Новые картинки должны быть активными. Уже сохранённую неактивную картинку
можно оставить у того же аудио в прежнем количестве; это не разрешает
добавлять новые неактивные связи.

### Изменение через админку и копирование

Сохранение изменённого состава в форме плейлиста отправляет новую редакцию
**всем активным единым заказам**, использующим этот плейлист. Изменение только
названия/описания и повторное сохранение того же состава новую команду не создают.
Если подготовка доставки не удалась, плейлист и редакции заказов откатываются.

Копирование создаёт отдельный плейлист с прежним порядком и привязками картинок.
Медиафайлы остаются общими, заказы автоматически не копируются. Чтобы изменить
акцию только для выбранных точек, используйте копию в их заказах. Обновлённый
Player догружает недостающие или повреждённые файлы, а готовые переиспользует.

Старые методы создания **`/api/adorders/`** и **`/api/bgorders/`** пока сохранены.

### Legacy-операции **`add_files`** и **`remove_files`**

```http
POST /api/playlists/{playlist_id}/add_files/
POST /api/playlists/{playlist_id}/remove_files/

{
  "files": ["00000000-0000-0000-0000-000000000011"]
}
```

Эти функции согласуют основные файлы и структурированные элементы. Новые файлы
добавляются в конец; у оставшихся аудио картинки сохраняются. При удалении аудио
удаляются его привязки, но сами медиафайлы остаются. Неизвестный UUID при удалении
игнорируется, при добавлении — отклоняется. Для изменения порядка или картинок
используйте `PATCH` с полным **`items`**. Простые плейлисты должны оставаться
одного типа; смешанный контент создаётся через **`items`**.

## 7. Единый заказ эфира

Новый endpoint объединяет фон и рекламу:

```text
/api/broadcast-orders/
```

Старые `/api/adorders/` и `/api/bgorders/` оставлены для совместимости. Новая
интеграция 1С создаёт заказы через `/api/broadcast-orders/`.

### Основные поля

| Поле | Нужно при создании | Кто заполняет | Назначение |
|---|---:|---|---|
| **`name`** | да | 1С | Понятное название, до 255 символов |
| **`description`** | нет | 1С | Номер документа, кампания или комментарий |
| **`placement`** | да | 1С | `background` или `advertising` |
| **`playback_policy`** | да | 1С | Правило воспроизведения |
| **`nomenclature`** | да | 1С | UUID одной точки |
| **`playlist`** | да | 1С | UUID плейлиста |
| **`starts_at`** | для рекламы | 1С | Начало периода в локальном времени точки |
| **`ends_at`** | для рекламы | 1С | Окончание периода |
| **`is_permanent`** | нет | 1С | Бессрочный фон без даты окончания |
| **`suppress_background_audio`** | нет | 1С | На время рекламы убрать фоновый звук |
| **`suppress_background_visual`** | нет | 1С | На время рекламы скрыть фоновое видео/картинки |
| **`parameters`** | зависит от правила | 1С | Частота, часы, вес, звук и время показа картинки |
| **`id`**, **`owner`**, **`created`** | нет | сервер | Служебные данные созданного заказа |
| **`status`**, **`revision`** | нет | сервер | Бизнес-статус и текущая редакция |
| **`delivery`**, **`actual_playback`** | нет | сервер и Player | Доставка и подтверждение эфира |

Дата и время передаются строго без суффикса часового пояса:

```text
YYYY-MM-DD HH:MM:SS
```

Например: `2026-10-10 09:00:00`. Значение трактуется как локальное время точки.

### **`placement`**: фон или реклама

| Значение | Что делает |
|---|---|
| **`background`** | Формирует постоянный или периодический фон: музыка, видео, картинки, ticker |
| **`advertising`** | Добавляет рекламные выходы поверх фона по выбранному расписанию |

**`placement`** определяет роль заказа. Тип файла сам по себе не превращает
контент в рекламный заказ.

### **`playback_policy`** и обязательные параметры

| Значение | Человеческое описание | Дополнительные поля **`parameters`** |
|---|---|---|
| **`workday`** | Равномерные выходы в рабочее время точки | **`times_in_hour`** |
| **`hourly_slots`** | Историческое имя равномерных выходов | **`times_in_hour`** |
| **`open_offset`** | Начать со смещением от открытия | **`times_in_hour`**, **`timedelta`** |
| **`close_offset`** | Работать до смещения перед закрытием | **`times_in_hour`**, **`timedelta`** |
| **`fixed_time`** | Выходы между двумя указанными часами | **`times_in_hour`**, **`start_time`**, **`end_time`** |
| **`open_to_fixed`** | От открытия до заданного часа | **`times_in_hour`**, **`end_time`** |
| **`fixed_to_close`** | От заданного часа до закрытия | **`times_in_hour`**, **`start_time`** |
| **`start_to_close`** | Первый выход в заданное время, затем до закрытия | **`times_in_hour`**, **`start_time`** |
| **`continuous`** | Непрерывная реклама вместо фона | **`times_in_hour`** не нужен и удаляется сервером |
| **`event`** | По событию Player | **`times_in_hour`**, **`event`**, **`active_ad`**; режим зарезервирован для будущего Player |

Для нового обычного расписания используйте **`workday`**. Значения
**`workday`** и **`hourly_slots`** сейчас доставляются Player одинаково.

Для **`background`** доступен только **`workday`**. Бессрочным может быть только
фон.

Все значения **`start_time`**, **`end_time`** и **`timedelta`** имеют формат
`HH:MM:SS`. Для часов начала и окончания диапазон часов `00–23`; для смещения
**`timedelta`** часы могут быть больше `23`.

### Общие значения **`parameters`**

| Поле | Тип и предел | Что меняет |
|---|---|---|
| **`times_in_hour`** | целое `1–60` | Сколько рекламных выходов планировать за час |
| **`weight`** | целое `0–100`, по умолчанию `50` | Приоритет очередности: большее значение начинает раньше; не частота выходов |
| **`audio_muted`** | `true` / `false` | Отключить звук самого рекламного ролика |
| **`image_duration_seconds`** | целое `1–86400` | Сколько секунд показывать каждую картинку визуального фона |

**`audio_muted`** и **`suppress_background_audio`** отвечают за разные звуки:

- **`audio_muted=true`** — рекламный файл проигрывается без своего звука;
- **`suppress_background_audio=true`** — фоновая музыка ставится на паузу на
  время рекламы.

Для **`continuous`** сервер автоматически устанавливает
**`suppress_background_visual=true`** и вычисляет подавление фонового звука из
**`audio_muted`**.

Например, видео с приоритетом 70 начинает раньше картинок с приоритетом 60.
Если картинки имеют больший приоритет, очередь начинается с них. Количество
рекламных выходов задаёт **`times_in_hour`**, а не **`weight`**.
Непрерывная реклама со звуком подавляет весь фон; без звука сохраняет фоновую
музыку, но занимает визуальный канал. Новый бессрочный фон заменяет прежний
после готовности контента: два последовательных бессрочных заказа не следует
использовать как способ чередования. Для совместной очереди видео и картинок
соберите один смешанный визуальный плейлист.

### Пример обычной рекламы

```http
POST /api/broadcast-orders/ HTTP/1.1
Host: api.example.ru
Authorization: access_token <JWT>
Content-Type: application/json

{
  "name": "РК-1042 — магазин Мира",
  "description": "Документ 1С РК-1042",
  "placement": "advertising",
  "playback_policy": "workday",
  "nomenclature": "00000000-0000-0000-0000-000000000101",
  "playlist": "00000000-0000-0000-0000-000000000201",
  "starts_at": "2026-10-10 09:00:00",
  "ends_at": "2026-10-20 18:00:00",
  "suppress_background_audio": true,
  "suppress_background_visual": false,
  "parameters": {
    "times_in_hour": 4,
    "audio_muted": false,
    "weight": 70
  }
}
```

### Пример бессрочного визуального фона

Один структурированный плейлист может содержать видео и картинки в общей
очереди. Это удобно, когда они являются одним комплектом и должны обновляться
вместе.

```json
{
  "name": "Главный визуальный фон",
  "placement": "background",
  "playback_policy": "workday",
  "nomenclature": "00000000-0000-0000-0000-000000000101",
  "playlist": "00000000-0000-0000-0000-000000000202",
  "is_permanent": true,
  "parameters": {
    "weight": 50,
    "image_duration_seconds": 12
  }
}
```

Для такого фона Player должен сообщить поддержку
`background_visual_queue_version=1`. Если Player старый, сервер вернёт ошибку
доставки с просьбой обновить его, а не молча потеряет часть поведения.

### Изменение заказа

```http
PATCH /api/broadcast-orders/{order_id}/ HTTP/1.1
Authorization: access_token <JWT>
Content-Type: application/json

{
  "ends_at": "2026-10-31 18:00:00",
  "parameters": {
    "times_in_hour": 6,
    "audio_muted": false,
    "weight": 70
  }
}
```

После изменения сервер увеличивает **`revision`** и отправляет Player полную
новую редакцию. Поле **`parameters`** тоже заменяется целым объектом: включите
в него все ключи, которые нужно сохранить.

Нельзя менять **`nomenclature`** и **`placement`**. Для другой точки или другой
роли в эфире отмените старый заказ и создайте новый.

### Отмена

```http
POST /api/broadcast-orders/{order_id}/cancel/ HTTP/1.1
Authorization: access_token <JWT>
Content-Type: application/json

{}
```

Ответ:

```json
{
  "detail": "Отмена запрошена; ожидается подтверждение Player."
}
```

Это подтверждение постановки команды в очередь. Окончательную отмену показывает
**`delivery.status="cancelled"`**.

### Повторная отправка

```http
POST /api/broadcast-orders/resend/ HTTP/1.1
Authorization: access_token <JWT>
Content-Type: application/json

{
  "order_ids": [
    "00000000-0000-0000-0000-000000000301",
    "00000000-0000-0000-0000-000000000302"
  ]
}
```

Допустимо от 1 до 100 уникальных UUID ожидающих или активных заказов. Метод не
меняет содержимое и **`revision`**; он только повторяет доставку.

## 8. Как читать ответ заказа

### Бизнес-статус **`status`**

| Значение | Значение для бизнеса |
|---:|---|
| `0` | Ожидает эфира |
| `1` | В эфире |
| `2` | Завершён |
| `3` | Отменён |
| `4` | Ошибка |

Этот статус недостаточен для диагностики доставки. Всегда читайте также
**`delivery`** и **`actual_playback`**.

### Доставка **`delivery`**

```json
{
  "desired_action": "apply",
  "revision": 2,
  "status": "applied",
  "applied_revision": 2,
  "on_air_revision": 2,
  "last_error": "",
  "progress": null
}
```

| **`delivery.status`** | Что означает |
|---|---|
| `queued` | Команда поставлена в очередь |
| `delivered` | Команда выдана Player |
| `received` | Получение подтверждено |
| `downloading` | Player загружает файлы |
| `ready` | Файлы готовы |
| `applied` | Расписание этой редакции применено |
| `cancelled` | Отмена подтверждена Player |
| `failed` | Player или сервер отклонил применение; причина в **`last_error`** |
| `superseded` | Команду заменила более новая редакция |

Во время подготовки **`delivery.progress`** может содержать:

- **`phase`**: `downloading`, `verifying` или `applying`;
- **`files_verified`** и **`files_total`**;
- **`received_at`**;
- **`fresh`** — получено ли наблюдение недавно.

Прогресс является наблюдением, а не квитанцией готовности. После финального
подтверждения он становится `null`, а результат отражается в
**`delivery.status`**.

### Фактический эфир **`actual_playback`**

| **`code`** | Что показывать пользователю 1С |
|---|---|
| `pending` | Текущая редакция ещё не применена |
| `awaiting_fact` | Заказ найден в состоянии Player, ожидается событие запуска |
| `on_air` | Эта редакция сейчас воспроизводится |
| `paused` | Воспроизведение поставлено на паузу |
| `off_air` | Заказ готов, но сейчас не воспроизводится |
| `cancelling` | Отмена ждёт подтверждения |
| `cancelled` | Отменён |
| `delivery_error` | Ошибка доставки или применения |
| `playback_error` | Последний подтверждённый выход завершился ошибкой |
| `unknown` | Серверу не хватает свежих данных для точного вывода |

**`unknown`** не следует автоматически превращать в ошибку заказа. Например,
точка может быть временно не на связи или работать на старом протоколе.

### Пример чтения одного заказа

```http
GET /api/broadcast-orders/{order_id}/ HTTP/1.1
Authorization: access_token <JWT>
```

Для пакетной сверки используйте список с фильтрами:

```http
GET /api/broadcast-orders/?nomenclature={point_id}&status=1&limit=100
GET /api/broadcast-orders/?placement=advertising&playback_policy=workday
GET /api/broadcast-orders/?name=РК-1042
```

## 9. Репликации, квитанции и фактическая статистика

Эти понятия не равны друг другу.

| Понятие | Смысл | Где смотреть из 1С |
|---|---|---|
| Заказ | Желаемое расписание | `/api/broadcast-orders/` |
| Репликация / команда | Техническая доставка изменения Player | **`delivery`** заказа; для старого протокола — `/api/tasks/{point_id}/tasks/` |
| Квитанция | Ответ Player о применении/ошибке команды | Проецируется в **`delivery.status`**, **`applied_revision`**, **`last_error`** |
| Событие эфира | Фактический запуск, пауза, завершение или ошибка | **`actual_playback`**; детальный журнал в админке |
| Legacy-статистика | Агрегированные факты старого контура | `/api/statistics/{point_id}/...` |
| План/факт | Сравнение расчётного числа выходов с завершёнными воспроизведениями | Сейчас отчёт в карточке заказа админки |

### История legacy-репликаций

```http
GET /api/tasks/{nomenclature_id}/tasks/?limit=100 HTTP/1.1
Authorization: access_token <JWT>
```

Этот endpoint полезен для диагностики старого протокола. Для нового единого
заказа основным источником является **`delivery`**, потому что он учитывает
конкретный **`order_id`** и **`revision`**.

### Legacy-статистика по точке

```http
GET /api/statistics/{nomenclature_id}/ad_stat/?date=2026-10-10
GET /api/statistics/{nomenclature_id}/music_stat/?date=2026-10
GET /api/statistics/{nomenclature_id}/video_stat/?date=2026
GET /api/statistics/{nomenclature_id}/image_stat/?date=2026-10-10
GET /api/statistics/{nomenclature_id}/ticker_stat/?date=2026-10-10
```

Параметр **`date`** принимает `YYYY-MM-DD`, `YYYY-MM` или `YYYY`. Ответ не
пагинируется и содержит **`file`**, **`played`**, **`length`**; реклама также
содержит **`ad_block`**.

Эти счётчики не нужно суммировать с новым журналом событий: это разные контуры,
и такое сложение может дать двойной факт.

### План/факт

Дневной план/факт строится по неизменяемому манифесту отправленной редакции и
завершённым событиям Player. Отчёт сейчас доступен сотруднику из карточки
единого заказа в админке. Публичного endpoint план/факт для 1С пока нет.

Расчёт плана использует текущее рабочее время точки, потому что историческая
копия графика работы Player пока не хранится. Фактические события при этом
жёстко привязаны к UUID заказа и номеру редакции.

## 10. Старый Player и новые интеграции

`POST /api/tasks/{nomenclature_id}/pending_tasks/` сохраняет `AllowAny` для
выпущенных ранее Player. UUID точки фактически служит там старым ключом доступа.
Это совместимость, а не рекомендуемый способ новой интеграции.

Новая 1С:

- всегда отправляет JWT даже в те GET-методы, которые исторически могут
  работать без него;
- не вызывает **`pending_tasks`** и `/api/station/v2/sync/`;
- не отправляет квитанции и статистику от имени Player;
- не использует UUID точки как секрет;
- не создаёт прямые legacy-заказы `/api/adorders/` и `/api/bgorders/`.

Новый Player получает **`station_token`** после JWT-защищённой привязки:
`POST /api/station/v2/bind/`. Затем только Player обращается к
`POST /api/station/v2/sync/` с заголовком `Station <station_token>`.

## 11. Как читать админку

Главная страница и боковое меню используют прежние разделы приложений:

| Раздел | Что здесь делать |
|---|---|
| **Номенклатуры** | Точки, установки, ключи и команды Player v2 |
| **Файлы** | Медиафайлы, плейлисты и их элементы |
| **Заказы** | Единые фоновые и рекламные заказы |

Раздел виден только при наличии прав на его объекты. Существующие URL, модели
и права не меняются; остальные справочники сохраняют свои обычные разделы.

Админка содержит бизнес-объекты и технические журналы. Удобно рассматривать её
по назначению описанных ниже объектов. Это пояснение, а не новые группы меню.

### Контент

- **Файлы** — загруженные аудио, видео, картинки и ticker.
- **Плейлисты** — наборы основных файлов и привязки картинок к аудио.
- **Элементы плейлиста** — строки состава; обычно их редактируют внутри
  плейлиста, а не как самостоятельный справочник.

### Эфир

- **Заказы эфира** — единые фоновые и рекламные заказы.
- В карточке заказа находятся доставка, фактический эфир и ссылка на
  план/факт.
- Старые рекламные и фоновые заказы нужны для исторических данных и
  совместимости.

### Точки и установки Player

- **Номенклатуры / точки вещания** — бизнес-карточка площадки и её UUID.
- **Установки Player** — конкретные установки программы, привязанные к точке.
- **Ключи доступа станций** — технические ключи Player; их не копируют в 1С.

### Диагностика Player

- **Команды Player v2** — журнал отправленных технических команд.
- **События эфира Player** — подтверждённые фактические события.
- **Состояние синхронизации / присутствия** — когда Player отвечал и какой
  протокол поддерживает.
- **Legacy-репликации и квитанции статистики** — нужны при разборе старого
  транспорта.

Оператор 1С обычно работает с точкой, файлами, плейлистом и заказом. Команды,
ключи, receipts и события нужны разработчику или техподдержке при диагностике.

## 12. Ошибки и безопасные повторы

| HTTP | Что означает | Действие 1С |
|---:|---|---|
| `200` | Операция выполнена | Обработать тело ответа |
| `201` | Объект создан | Сохранить UUID из ответа |
| `400` | Поля или состояние не прошли проверку | Показать ошибки по именам полей, не повторять без исправления |
| `401` | JWT отсутствует, истёк или имеет неправильный префикс | Обновить access token и повторить один раз |
| `403` | У пользователя нет права на операцию или точку | Не повторять автоматически; проверить роль и доступ |
| `404` | UUID не найден | Обновить сопоставление справочников |
| `5xx` | Временная ошибка сервера или зависимости | Повторить с задержкой после проверки результата |

У API нет общего **`Idempotency-Key`** для создания. После таймаута нельзя
сразу повторять `POST` или `PATCH`:

1. Выполните `GET` по сохранённому UUID или найдите объект по собственному
   идентификатору, включённому в **`name`**/**`description`**.
2. Сравните содержимое и **`revision`**.
3. Повторите изменение только если сервер его не принял.

Повторный `PATCH` заказа увеличивает **`revision`** ещё раз. Повторный `POST`
может создать второй заказ или плейлист.

## 13. Рекомендуемый алгоритм обмена 1С

1. Получить или обновить JWT.
2. Найти точку по точному **`code1c`** и сохранить её UUID.
3. Для каждого файла проверить, известен ли его серверный UUID; при
   необходимости загрузить файл.
4. Создать плейлист через **`items`**. Для обновления отправлять полный снимок
   **`items`**.
5. Создать один `/api/broadcast-orders/` для одной точки.
6. Сохранить **`order.id`** и **`revision`**.
7. Периодически читать заказ до `delivery.status=applied` либо `failed`.
8. Для оперативного состояния показывать **`actual_playback.code`**.
9. Для прекращения размещения вызвать **`cancel`** и дождаться
   `delivery.status=cancelled`.
10. Для аналитики не смешивать legacy-статистику с новым журналом фактов.
