# API вещания для интеграции с 1С

Этот документ описывает рабочий сценарий от данных 1С до фактического эфира:
как выбрать точку, загрузить контент, собрать плейлист, создать заказ и понять,
что именно сделал Player.

Примеры используют адрес `https://api.example.ru`. Замените его адресом среды.
UUID и токены в примерах вымышлены.

Интерактивные версии схемы доступны в приложении:

- `GET /api/docs/` — Swagger UI;
- `GET /api/redoc/` — ReDoc;
- `GET /api/schema/` — схема OpenAPI (`?format=json` для JSON).
- `GET /docs/` — ReDoc из той же актуальной схемы;
- `GET /api/integration-guide.md` — это руководство для передачи разработчику 1С.

## 1. Как устроен обмен

```text
1С / оператор
    │  JWT: access_token <JWT>
    ▼
Backend API
    │  создаёт команду и следит за её редакцией
    ▼
Content Player
    │  Station <station_token>
    ├─ подтверждает доставку и применение
    └─ отправляет события фактического воспроизведения
```

У системы два разных контура.

| Контур | Кто обращается | Заголовок **`Authorization`** | Для чего |
|---|---|---|---|
| Управление | 1С, веб-интерфейс, сотрудники | `access_token <JWT>` | Точки, файлы, плейлисты, заказы, просмотр состояния |
| Станция | Установленный Content Player | `Station <station_token>` | Получение команд, квитанции доставки, состояние и факты эфира |

1С использует только контур управления. **`station_token`** нельзя хранить в 1С
и нельзя передавать в запросы файлов, плейлистов или заказов.

### Что означает «успешно» на разных этапах

| Этап | Где смотреть | Что подтверждено |
|---|---|---|
| API принял запрос | HTTP `200` или `201` | Данные прошли проверку и записаны на сервере |
| API принял часть точек | HTTP `207` | Сохранены только успешные элементы ответа; остальные содержат причину отказа |
| Загрузка и применение | Админ-панель | Player подтвердил загрузку файлов и применение заказа |
| Контент вышел в эфир | **`status=1`** | Player сообщил о запуске/завершении воспроизведения |

HTTP `201` при создании заказа не означает, что ролик уже скачан или проигран.

## 2. Авторизация 1С

### Получение токенов

```http
POST /auth/jwt/create/ HTTP/1.1
Host: api.example.ru
Content-Type: application/json

{
  "email": "integration@example.ru",
  "password": "<пароль из защищённого хранилища>"
}
```

Ответ:

```json
{
  "refresh": "<refresh JWT>",
  "access": "<access JWT>"
}
```

Во всех рабочих запросах передавайте **`access`** так:

```http
Authorization: access_token <access JWT>
```

В этом проекте используется префикс **`access_token`**, а не `Bearer`.

### Обновление access token

```http
POST /auth/jwt/refresh/ HTTP/1.1
Host: api.example.ru
Content-Type: application/json

{
  "refresh": "<refresh JWT>"
}
```

Сервер включает ротацию refresh token. Если в ответе пришёл новый
**`refresh`**, 1С должна атомарно сохранить его вместе с новым **`access`**.
Пароль и токены нельзя писать в журнал запросов 1С.

## 3. Идентификаторы: что хранить в 1С

| Поле | Сущность | Для чего хранить |
|---|---|---|
| **`code1c`** | Точка вещания | Стабильный бизнес-ключ для поиска точки по данным 1С |
| **`id`** точки | Точка вещания | UUID, который передаётся в заказе как элемент **`clients`** |
| **`file.id`** | Медиафайл | UUID файла для состава плейлиста |
| **`playlist.id`** | Плейлист | UUID набора контента для заказа |
| **`order.id`** | Заказ эфира | UUID для чтения состояния, изменения и отмены |
| **`installation_id`** | Установка Player | Технический идентификатор установки; обычно 1С не нужен |

Не используйте **`id_tachka`** или название точки как внешний ключ заказа.
Название может измениться, а технические поля старых Player не являются
контрактом 1С.

## 4. Найти точку вещания

Точка вещания в API называется **номенклатурой**. Карточку можно получить по
UUID или по **`code1c`**. Для первичной привязки 1С используйте точный код:

```http
GET /api/nomenclatures/0000012345/ HTTP/1.1
Host: api.example.ru
Authorization: access_token <JWT>
```

Фрагмент ответа:

```json
{
  "id": "00000000-0000-0000-0000-000000000101",
  "name": "Магазин на Мира, 10",
  "code1c": "0000012345"
}
```

Сохраните **`id`** как UUID точки. Ответ `404` означает, что сопоставление
справочника отсутствует; заказ создавать нельзя, пока оператор не исправит
привязку.

Для спискового и ручного поиска доступен
`GET /api/nomenclatures/?code1c=...`, а также фильтры **`search`**, **`name`**,
**`id`**, **`brand_id`**, **`status`** и другие. Ответ списка сокращён и имеет
поля **`count`**, **`next`**, **`previous`**, **`results`**. Автоматический обмен
1С должен использовать прямой запрос карточки по точному **`code1c`**.

## 5. Загрузка файлов

### Типы файлов

| **`type`** | API-тип | Назначение |
|---:|---|---|
| `0` | `music` | Музыка или обычное аудио |
| `1` | `video` | Видео |
| `2` | `image` | Изображение |
| `3` | `ticker` | Бегущая строка |
| `4` | `ad` | Рекламный файл |

Подтип файла в админке служит для классификации и не определяет правила
заказа. То, является ли заказ рекламным, задаёт **`type`** заказа.

### Новый JSON-запрос

`POST /api/files/` принимает JSON. Поле **`source`** имеет исторический формат:

```text
name:<имя>.<расширение>;base64,<данные base64>
```

Пример:

```http
POST /api/files/ HTTP/1.1
Host: api.example.ru
Authorization: access_token <JWT>
Content-Type: application/json

{
  "type": 4,
  "source": "name:promo-october.mp3;base64,SUQzBAAAAAAA...",
  "tags": [
    {"name": "1С"},
    {"name": "Кампания РК-1042", "color": "#3874CB"}
  ]
}
```

Успешный ответ `201` содержит созданный **`id`**, вычисленные **`hash`**,
**`size`**, **`length`**, имя и временную ссылку **`url`**. URL не храните как
постоянный: срок подписанной ссылки ограничен, для скачивания запрашивайте файл
снова.

`POST /api/source/` принимает multipart-файл, но помечен как устаревший и
сохранён для старой админки. Новая интеграция 1С использует `/api/files/`.

### Поиск уже загруженного файла

Перед повторной загрузкой можно искать по контрольной сумме или имени:

```http
GET /api/files/?hash=<md5+sha256>
GET /api/files/?name=promo-october
GET /api/files/?search=РК-1042
```

**`hash`** — серверная комбинация MD5 и SHA-256. При таймауте после `POST`
сначала выполните поиск: слепой повтор может вернуть ошибку дубликата.

## 6. Плейлисты

Плейлист отвечает на вопрос **«какие файлы и в каком порядке воспроизводить»**.
Заказ отдельно отвечает на вопросы **«на какой точке, в какой период и по
какому правилу»**.

### Состав плейлиста: **`files`**

Плейлист хранит только основные файлы и их порядок. Прикрепление картинок
к рекламному аудио является настройкой **заказа**, а не общего плейлиста.
Один плейлист можно использовать в разных заказах с разным сопровождением.

```http
POST /api/playlists/ HTTP/1.1
Authorization: access_token <JWT>
Content-Type: application/json

{
  "name": "Ролики осенней акции",
  "files": [
    "00000000-0000-0000-0000-000000000011",
    "00000000-0000-0000-0000-000000000012"
  ]
}
```

**`owner`** в ответах плейлиста — объект **`id`** (UUID автора) и **`full_name`** (ФИО).
Автор определяется по токену.

**`files`** — массив UUID в нужном порядке. Очередь сохраняется именно в порядке
добавления; при включённом случайном воспроизведении Player выбирает файлы случайно. Поддерживаются аудио, видео,
самостоятельные картинки и другие виды контента; смешанный визуальный фон
собирается видео и картинками в одном массиве. Основные UUID не повторяются;
допускается 1–1000 основных файлов.

```http
GET /api/playlists/{playlist_id}/
PATCH /api/playlists/{playlist_id}/
```

В ответе **`files`** содержит **`id`**, **`name`**, **`type`**, **`url`**.
Типы имеют понятные названия: **`audio`**, **`video`**, **`image`** и другие.
URL сохраняются из старого API, но не заменяют постоянный UUID файла.

Переданный при PATCH **`files`** заменяет полный основной список и порядок.
Без этого поля состав остаётся прежним. **`name`** и **`description`** можно
изменять отдельно. Поле **`audio_images`** в плейлисте не принимается:
задавайте его в заказе.

### Изменение состава, копирование и активные заказы

Изменение состава отправляет обновление всем активным единым заказам этого
плейлиста. При этом сопровождение каждого заказа остаётся его собственным:
картинки сохранённых аудио не меняются, привязки удалённых аудио убираются
только из соответствующих заказов. Добавленные аудио изначально не имеют картинок.



Повтор того же состава и изменение только названия не создают лишнюю команду.
Ошибка подготовки команд откатывает изменение плейлиста и заказов вместе.
Пустой состав разрешён только без активных заказов. При активных старых
BgOrder/AdOrder полная замена ограничена прежними правилами.

Копирование плейлиста копирует основные файлы и порядок; заказы и их картинки
не копируются. Чтобы изменить картинку только для одного магазина, измените
соответствующий заказ. При обновлении Player догружает недостающие или
повреждённые файлы, а готовые переиспользует.

Старые методы создания **`/api/adorders/`** и **`/api/bgorders/`** сохранены.
Новые привязки картинок создаются только в рекламном заказе.

### Добавить или убрать основные файлы

```http
POST /api/playlists/{playlist_id}/add_files/
POST /api/playlists/{playlist_id}/remove_files/

{
  "files": ["00000000-0000-0000-0000-000000000011"]
}
```

Новые файлы добавляются в конец. Удаление аудио убирает его сопровождение из
активных связанных единых заказов; картинки оставшихся аудио сохраняются.
Для порядка используйте PATCH плейлиста; для сопровождения — PATCH заказа.
## 7. Единый заказ эфира

Новый endpoint объединяет фон и рекламу:

```text
/api/broadcast-orders/
```

Старые `/api/adorders/` и `/api/bgorders/` оставлены для совместимости. Новая
интеграция 1С создаёт заказы через `/api/broadcast-orders/`.

### Основные поля

| Поле | Назначение |
|---|---|
| **`name`**, **`description`** | Название и комментарий |
| **`type`** | **`bg`** — фон; **`ad`** — реклама |
| **`clients`** | Массив UUID номенклатур (точек), даже для одной точки; в ответе — объекты **`id`**, **`name`** |
| **`playlist`** | UUID плейлиста; состав и URL файлов получайте отдельным методом плейлистов |
| **`audio_images`** | Только реклама: UUID аудио из плейлиста → массив UUID картинок в порядке показа |
| **`broadcast_interval`** | Объект **`lower`**, **`upper`**: начало и конец периода |
| **`broadcast_type`** | Числовое правило расписания рекламы, как в старом API |
| **`order_type`** | Только в ответе фона: тип медиа 0 — музыка, 1 — видео/общая визуальная очередь, 2 — картинки, 3 — ticker |
| **`is_permanent`** | Бессрочный резервный фон без даты окончания |
| **`parameters`** | Частота, вес, дни, часы, звук и длительность фоновых картинок |
| **`suppress_background_audio`**, **`suppress_background_visual`** | Приостановить соответствующий фон на время рекламы |
| **`status`** | Бизнес-статус заказа; 1 — подтверждён первый выход |
| **`owner`** | Автор: **`id`** и **`full_name`**; заполняется сервером |

Передавайте **`clients`** как массив UUID: для одной точки — один элемент,
для нескольких — несколько. Сервер создаёт отдельный заказ для каждой точки
и всегда возвращает массив записей в порядке запроса. Повторы UUID, неверный
формат UUID и некорректные общие параметры отклоняют запрос до создания заказов.
Неизвестная, неактивная или несовместимая точка получает свой отказ; для остальных
точек заказы создаются. Заказ и команда конкретной точки сохраняются вместе:
при её ошибке не остаётся незавершённого заказа или команды.

**HTTP 201** означает, что созданы все заказы. **HTTP 207** — частичный успех:
в одном массиве возвращаются созданные заказы и объекты отказа вида:

```json
{
  "client": "00000000-0000-0000-0000-000000000102",
  "error": "Player этой точки не поддерживает выбранный функционал. Обновите Player."
}
```

**`client`** здесь — UUID номенклатуры, **`error`** — причина, почему заказ для неё
не создан. Если отказ получили все точки, HTTP 400 содержит массив таких ошибок.
Общие ошибки полей по-прежнему возвращаются объектом с именами полей.
При частичном успехе повторяйте запрос только для неуспешных UUID: повтор всей
группы создаст дополнительные заказы и для уже успешных точек.

Дата и время в **`broadcast_interval.lower`** и **`upper`** передаются без
часового пояса: **`YYYY-MM-DD HH:MM:SS`**, по местному времени точки. У рекламы
обе границы обязательны. Для бессрочного фона **`upper=null`**; период можно
не передавать, чтобы начать после доставки. При PATCH передайте обе границы
объекта периода. **`type`** определяет роль заказа, не формат медиафайла.

### Картинки к рекламному аудио — свойство заказа

Один плейлист можно использовать в нескольких заказах с разными картинками.
Привязки задаются полем **`audio_images`** верхнего уровня заказа, а не внутри
**`parameters`** и не в плейлисте. Пример фрагмента POST или PATCH:

```json
{
  "audio_images": {
    "00000000-0000-0000-0000-000000000011": [
      "00000000-0000-0000-0000-000000000021",
      "00000000-0000-0000-0000-000000000022"
    ]
  }
}
```

Ключ — UUID основного аудиофайла выбранного плейлиста; значения — UUID картинок.
В примере ключ `...011` обозначает аудиоролик, а `...021` и `...022` — картинки
к этому ролику. Для каждого другого аудиофайла добавляется отдельный ключ с его
UUID и свой массив картинок. Порядок массива — порядок показа. Идентификаторы
берутся из **`id`** файла: здесь не используются названия, URL или UUID плейлиста.

**`additionalProp1`**, **`additionalProp2`** в автоматически созданных примерах —
заглушки документации, а не названия полей для отправки. Вместо них укажите
UUID аудиофайлов. Все UUID примера замените на идентификаторы загруженных файлов.

Для поиска загруженных картинок используйте `GET /api/files/?file_type=2&name=...`;
UUID берите из **`id`** ответа. Ссылку для предпросмотра получайте в **`url`** файла.
Картинки не добавляйте в основные **`files`** плейлиста, если они должны только
сопровождать аудио. Player загрузит их вместе с заказом. Одна картинка занимает
всё аудио; несколько делят его длительность поровну, без ручного задания времени.
Другие ролики плейлиста воспроизводятся обычным образом.

При новом назначении все файлы должны быть активны; родитель должен быть аудио,
дети — изображениями, без повторов у одного аудио. Ограничения: до 1000 аудио,
до 10 000 ссылок на картинки суммарно. Ответ заказа возвращает ту же карту UUID,
без дополнительных URL.

### Правила рекламы **`broadcast_type`**

| Значение | Правило | Параметры |
|---|---|---|
| **`0`** | В рабочее время точки | **`times_in_hour`** |
| **`1`** | После открытия со смещением | **`times_in_hour`**, **`timedelta`** |
| **`2`** | До закрытия со смещением | **`times_in_hour`**, **`timedelta`** |
| **`3`** | Между фиксированными часами | **`times_in_hour`**, **`start_time`**, **`end_time`** |
| **`4`** | От открытия до указанного часа | **`times_in_hour`**, **`end_time`** |
| **`5`** | От указанного часа до закрытия | **`times_in_hour`**, **`start_time`** |
| **`6`** | По событию | Зарезервировано; не используйте до реализации событий |
| **`7`** | Непрерывная реклама вместо фона | Частота не нужна |

Для начала ежедневного рекламного окна в заданный час используйте
**`broadcast_type=5`** и **`parameters.start_time`**. Первый плановый выход —
в начале окна, далее выходы распределяются с интервалом 3600 / **`times_in_hour`**
секунд. Окно ограничивается периодом заказа и рабочим временем точки.
Фону рекламная частота и числовой **`broadcast_type`** не назначаются.

### **`parameters`**

| Поле | Значение | Назначение |
|---|---|---|
| **`times_in_hour`** | Целое 1–60 | Число рекламных выходов заказа за час, не каждого файла |
| **`weight`** | Целое 0–100, по умолчанию 50 | Приоритет очередности; не частота |
| **`weekdays`** | Разные целые 0–6 | 0 — пн, 1 — вт, 2 — ср, 3 — чт, 4 — пт, 5 — сб, 6 — вс; без поля ежедневно |
| **`audio_muted`** | true/false | Отключить звук рекламного ролика |
| **`image_duration_seconds`** | Целое 1–86400 | Время каждой фоновой картинки; не применяется к картинкам рекламного аудио |
| **`start_time`**, **`end_time`** | HH:MM:SS | Часы расписания |
| **`timedelta`** | HH:MM:SS | Смещение относительно открытия/закрытия |

**`weekdays`** ограничивает календарные дни местного времени дополнительно к
периоду дат. Пустой список, повторы, строки и значения вне 0–6 отклоняются.
Для всех дней пропустите поле или передайте все семь чисел. Выбранные дни
работают и у непрерывной рекламы. Для ограничений нужен обновлённый Player с
**`order_schedule_version=1`**, иначе сервер вернёт понятную ошибку.

Бессрочный фон остаётся ежедневным резервом. Ограниченные дни задавайте
отдельному временному фоновому заказу: в подходящее расписание он вытесняет
резерв своего канала; вне расписания снова играет резерв. Уже запущенный фоновый
ролик завершается естественно, следующий выбирается по актуальному расписанию.
Непрерывная реклама проверяет дни и во время показа.

При **`audio_muted=true`** реклама проигрывается без своего звука.
**`suppress_background_audio`** отдельно управляет фоновой музыкой. Для
непрерывной рекламы визуальный фон подавляется всегда, фоновая музыка
продолжает играть только при отключённом звуке рекламы. Дополнительные опции
требуют заявленной поддержки Player; старому ПО они не отправляются молча.

### Массовое создание рекламы

```json
{
  "name": "РК-1042 — магазины сети",
  "type": "ad",
  "clients": [
    "00000000-0000-0000-0000-000000000101",
    "00000000-0000-0000-0000-000000000102"
  ],
  "playlist": "00000000-0000-0000-0000-000000000201",
  "broadcast_interval": {
    "lower": "2026-10-13 09:00:00",
    "upper": "2026-11-01 18:00:00"
  },
  "broadcast_type": 0,
  "parameters": {"times_in_hour": 4, "weekdays": [0, 1, 2, 3, 4], "weight": 70}
}
```

### Формат ответа создания

Даже для одной точки ответ — массив. Каждый элемент относится к одной точке:

```json
[
  {
    "id": "00000000-0000-0000-0000-000000000301",
    "name": "РК-1042 — магазины сети",
    "type": "ad",
    "clients": [{"id": "00000000-0000-0000-0000-000000000101", "name": "Магазин на Мира"}],
    "owner": {"id": "00000000-0000-0000-0000-000000000401", "full_name": "Иванов Иван Иванович"},
    "status": 0
  }
]
```

Это фрагмент ответа; остальные поля описаны в таблице выше. Автор определяется
по пользователю токена, вручную **`owner`** в запросе не задаётся.

### Бессрочный резервный фон

```json
{
  "name": "Основной визуальный фон",
  "type": "bg",
  "clients": ["00000000-0000-0000-0000-000000000101"],
  "playlist": "00000000-0000-0000-0000-000000000202",
  "is_permanent": true,
  "parameters": {"weight": 50, "image_duration_seconds": 12}
}
```

Для временного фона передайте **`is_permanent=false`**, **`broadcast_interval`**
и нужные **`parameters.weekdays`**. Для рекламы с расчётной частотой план за
невыбранный день равен нулю; фактические выходы сохраняются в статистике.

### Как пересекаются временные фоновые заказы

Видео и картинки образуют общую визуальную очередь. Активные временные заказы
заменяют бессрочный визуальный резерв. В начале очереди идёт заказ с большим
**`parameters.weight`**; далее берётся по одному файлу из каждого заказа.
Например, заказ A с приоритетом 70 содержит A1 и A2, заказ B с приоритетом 60 —
B1 и B2: **A1 → B1 → A2 → B2**. Больший приоритет не увеличивает частоту и не
исключает остальные заказы. При одинаковом приоритете порядок определяется UUID.
Видео доигрывает полностью, картинка показывается заданное время. После смены
даты или дня недели текущий файл доигрывает; следующий выбирается из подходящих
заказов. Если временных заказов больше нет, возвращается бессрочный резерв.

У фоновой музыки сейчас другое правило: среди подходящих временных заказов
выбирается один с самой поздней датой начала. Музыкальные плейлисты между собой
не чередуются, **`weight`** на этот выбор не влияет.

### Изменение заказа

`PATCH /api/broadcast-orders/{order_id}/` изменяет существующий заказ.
**`clients`** используется только при создании. Для смены точки или **`type`**
отмените старый заказ и создайте новый. **`parameters`** заменяется целиком:
включайте все ключи, которые нужно сохранить.

**`audio_images`** сохраняется независимо от **`parameters`**. Пропущенное поле
сохраняет картинки, `{}` очищает их, объект полностью заменяет карту.
Изменение только картинок не сбрасывает частоту, вес и расписание. При замене
плейлиста передайте подходящую карту либо `{}`: ссылки на отсутствующее в новом
плейлисте аудио отклоняются.

### Отмена

```http
POST /api/broadcast-orders/{order_id}/cancel/ HTTP/1.1
Authorization: access_token <JWT>
Content-Type: application/json

{}
```

Ответ:

```json
{
  "detail": "Отмена запрошена; ожидается подтверждение Player."
}
```

Это подтверждение постановки команды в очередь. Окончательную отмену показывает
**`status=3`** заказа после подтверждения Player.

### Повторная отправка

```http
POST /api/broadcast-orders/resend/ HTTP/1.1
Authorization: access_token <JWT>
Content-Type: application/json

{
  "order_ids": [
    "00000000-0000-0000-0000-000000000301",
    "00000000-0000-0000-0000-000000000302"
  ]
}
```

Допустимо от 1 до 100 уникальных UUID ожидающих или активных заказов. Метод не
меняет содержимое заказа; он только повторяет отправку.

## 8. Как читать ответ заказа

### Бизнес-статус **`status`**

| Значение | Значение для бизнеса |
|---:|---|
| `0` | Ожидает эфира |
| `1` | В эфире |
| `2` | Завершён |
| `3` | Отменён |
| `4` | Ошибка |

Подробности загрузки и применения заказа доступны в админ-панели.

Переход **`0 → 1`** происходит после первого принятого события **`started`**
для текущей применённой версии заказа. Скачивание и применение без реального
запуска этот переход не выполняют. **`status=1`** подтверждает, что заказ уже
начал выходить. Последующие выходы учитываются в статистике и отчёте план/факт;
текущее воспроизведение смотрите в состоянии эфира точки. Отменённые и завершённые заказы старое событие
не возвращает в эфир.

### Пример чтения одного заказа

```http
GET /api/broadcast-orders/{order_id}/ HTTP/1.1
Authorization: access_token <JWT>
```

Для пакетной сверки используйте список с фильтрами:

```http
GET /api/broadcast-orders/?clients={point_id}&status=1&limit=100
GET /api/broadcast-orders/?type=ad
GET /api/broadcast-orders/?name=РК-1042
```

## 9. Репликации, квитанции и фактическая статистика

Эти понятия не равны друг другу.

| Понятие | Смысл | Где смотреть из 1С |
|---|---|---|
| Заказ | Желаемое расписание | `/api/broadcast-orders/` |
| Репликация / команда | Техническая доставка изменения Player | Админ-панель; для старого протокола — `/api/tasks/{point_id}/tasks/` |
| Квитанция | Ответ Player о применении/ошибке команды | Статус загрузки и применения в админ-панели |
| Событие эфира | Подтверждённый факт воспроизведения Player | Первый запуск — **`status=1`**; последующие выходы — статистика и план/факт |
| Legacy-статистика | Агрегированные факты старого контура | `/api/statistics/{point_id}/...` |
| План/факт | Сравнение расчётного числа выходов с завершёнными воспроизведениями | Сейчас отчёт в карточке заказа админки |

### История legacy-репликаций

```http
GET /api/tasks/{nomenclature_id}/tasks/?limit=100 HTTP/1.1
Authorization: access_token <JWT>
```

Этот endpoint полезен для диагностики старого протокола. Для нового единого
заказа подробности отправки и применения доступны в админ-панели.

### Legacy-статистика по точке

```http
GET /api/statistics/{nomenclature_id}/ad_stat/?date=2026-10-10
GET /api/statistics/{nomenclature_id}/music_stat/?date=2026-10
GET /api/statistics/{nomenclature_id}/video_stat/?date=2026
GET /api/statistics/{nomenclature_id}/image_stat/?date=2026-10-10
GET /api/statistics/{nomenclature_id}/ticker_stat/?date=2026-10-10
```

Параметр **`date`** принимает `YYYY-MM-DD`, `YYYY-MM` или `YYYY`. Ответ не
пагинируется и содержит **`file`**, **`played`**, **`length`**; реклама также
содержит **`ad_block`**.

Эти счётчики не нужно суммировать с новым журналом событий: это разные контуры,
и такое сложение может дать двойной факт.

### План/факт

Дневной план/факт строится по неизменяемому манифесту отправленной редакции и
завершённым событиям Player. Отчёт сейчас доступен сотруднику из карточки
единого заказа в админке. Публичного endpoint план/факт для 1С пока нет.

Расчёт плана использует текущее рабочее время точки, потому что историческая
копия графика работы Player пока не хранится. Фактические события при этом
жёстко привязаны к UUID заказа и номеру редакции.

## 10. Старый Player и новые интеграции

`POST /api/tasks/{nomenclature_id}/pending_tasks/` сохраняет `AllowAny` для
выпущенных ранее Player. UUID точки фактически служит там старым ключом доступа.
Это совместимость, а не рекомендуемый способ новой интеграции.

Новая 1С:

- всегда отправляет JWT даже в те GET-методы, которые исторически могут
  работать без него;
- не вызывает **`pending_tasks`** и `/api/station/v2/sync/`;
- не отправляет квитанции и статистику от имени Player;
- не использует UUID точки как секрет;
- не создаёт прямые legacy-заказы `/api/adorders/` и `/api/bgorders/`.

Новый Player получает **`station_token`** после JWT-защищённой привязки:
`POST /api/station/v2/bind/`. Затем только Player обращается к
`POST /api/station/v2/sync/` с заголовком `Station <station_token>`.

## 11. Как читать админку

Главная страница и боковое меню используют прежние разделы приложений:

| Раздел | Что здесь делать |
|---|---|
| **Номенклатуры** | Точки, установки, ключи и команды Player v2 |
| **Файлы** | Медиафайлы, плейлисты и их элементы |
| **Заказы** | Единые фоновые и рекламные заказы |

Доступ к каждому разделу зависит от прав пользователя.

Админка содержит бизнес-объекты и технические журналы. Удобно рассматривать её
по назначению описанных ниже объектов. Это пояснение, а не новые группы меню.

### Контент

- **Файлы** — загруженные аудио, видео, картинки и ticker.
- **Плейлисты** — наборы основных файлов и их порядок.
- В карточке плейлиста есть **«Очередь файлов»**: существующие файлы можно заменить
  или удалить. Новые выбирайте с Ctrl (на macOS — Cmd); порядок добавления виден
  в нумерованном предпросмотре. Они добавляются в конец, ручные позиции не нужны.

### Эфир

- **Заказы эфира** — единые фоновые и рекламные заказы.
- В рекламном заказе после выбора плейлиста настройте картинки для каждого
  аудио в отдельном блоке: названия роликов и выбор изображений, без JSON.
  Порядок изображений определяет порядок показа; время делится автоматически.
- В карточке заказа находятся доставка, подтверждение первого запуска и ссылка
  на план/факт.
- Старые рекламные и фоновые заказы нужны для исторических данных и
  совместимости.

### Точки и установки Player

- **Номенклатуры / точки вещания** — бизнес-карточка площадки и её UUID.
- **Установки Player** — конкретные установки программы, привязанные к точке.
- **Ключи доступа станций** — технические ключи Player; их не копируют в 1С.

### Диагностика Player

- **Команды Player v2** — журнал отправленных технических команд.
- **События эфира Player** — подтверждённые фактические события.
- **Состояние синхронизации / присутствия** — когда Player отвечал и какой
  протокол поддерживает.
- **Legacy-репликации и квитанции статистики** — нужны при разборе старого
  транспорта.

Оператор 1С обычно работает с точкой, файлами, плейлистом и заказом. Команды,
ключи, receipts и события нужны разработчику или техподдержке при диагностике.

## 12. Ошибки и безопасные повторы

| HTTP | Что означает | Действие 1С |
|---:|---|---|
| `200` | Операция выполнена | Обработать тело ответа |
| `201` | Объект создан | Сохранить UUID из ответа |
| `207` | Часть заказов создана | Сохранить успешные заказы, показать **`client`** и **`error`** остальных; не повторять успешные UUID |
| `400` | Поля или состояние не прошли проверку | Показать ошибки полей либо массив отказов по точкам; исправить перед повтором |
| `401` | JWT отсутствует, истёк или имеет неправильный префикс | Обновить access token и повторить один раз |
| `403` | У пользователя нет права на операцию или точку | Не повторять автоматически; проверить роль и доступ |
| `404` | UUID не найден | Обновить сопоставление справочников |
| `5xx` | Временная ошибка сервера или зависимости | Повторить с задержкой после проверки результата |

У API нет общего **`Idempotency-Key`** для создания. После таймаута нельзя
сразу повторять `POST` или `PATCH`:

1. Выполните `GET` по сохранённому UUID или найдите объект по собственному
   идентификатору, включённому в **`name`**/**`description`**.
2. Сравните содержимое объекта.
3. Повторите изменение только если сервер его не принял.

Повторный `PATCH` заказа повторно отправляет настройки Player. Повторный `POST`
может создать второй заказ или плейлист.

## 13. Рекомендуемый алгоритм обмена 1С

1. Получить или обновить JWT.
2. Найти точку по точному **`code1c`** и сохранить её UUID.
3. Для каждого файла проверить, известен ли его серверный UUID; при
   необходимости загрузить файл.
4. Создать плейлист через **`files`**. Для обновления отправлять полный список
   основных файлов в нужном порядке.
5. Создать `/api/broadcast-orders/` с **`clients`**.
   Привязки картинок к рекламному аудио передать в **`audio_images`** заказа.
6. Сохранить **`id`** каждого созданного заказа.
7. Периодически читать **`status`** заказа; загрузку и применение проверять в админ-панели.
8. Для подтверждения первого выхода показывать **`status`**.
9. Для прекращения размещения вызвать **`cancel`** и дождаться
   **`status=3`** после подтверждения Player.
10. Для аналитики не смешивать legacy-статистику с новым журналом фактов.
